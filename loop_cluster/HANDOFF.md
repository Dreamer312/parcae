# 交接手册：在循环语言模型里做 token 聚类

写于 2026-11-13，由本地会话里的 Claude 写给服务器上接手的 Claude。之前的讨论都发生在用户的笔记本上，你看不到那段对话，这份文件是你唯一的背景。

## 1. 我们在做什么

用户是做大模型研究的，想投一篇论文，暂定 ICML 2027。

**研究问题**：循环语言模型（looped LM，同一组层反复执行多次）每一轮处理的都是完整的 token 序列，每个状态都是词级别的表示。能不能在循环过程中把 token 状态聚成少量"概念"状态，在概念上继续循环，最后再回到 token 级别输出？灵感来自视觉里的聚类骨干网络（FEC、HCFormer），以及"循环收敛到不动点时 token 表示会自然成簇"这个现象。

**代码库**：Parcae（本仓库，fork 自 SandyResearch/parcae）。结构是 prelude 层、循环的 core 层、coda 层，每一轮循环都会把 prelude 的输出重新注入一次。

**现在处于第 0 阶段**：还没有写任何聚类模块。先做两件事：
1. 用官方放出的 checkpoint 跑一个只做推理的诊断，看"循环状态自然成簇"这个前提成不成立。
2. 在我们自己的集群上训一个 Parcae-140M 和一个同规模的 GPT-140M，作为后面所有对比的基线，同时测出真实的训练速度。

## 2. 环境和约束

- 集群是 k8s，任务都跑在容器里，能访问 HuggingFace 和 GitHub。
- 常驻 16–32 张 H100，之后可能换成 32 张 H200。H200 主要是显存更大，算力和 H100 接近。
- 140M 和 370M 的实验用单个 8 卡 pod 就够，可以同时跑 2–4 个。770M 以上需要跨节点，集群有没有多节点训练组件（比如 Kubeflow Training Operator）还没问到。
- ICML 2027 的官方征稿还没发布。第三方估计是 2027-01-16 交摘要、01-22 交全文，**未经确认**。

## 5. 你接下来要做的

按顺序：

1. **确认数据到位**。用户说会先把数据下到服务器。配置文件读的是 `/resource/data/fineweb-edu-shuffled/data/sample-100BT/train` 和 `.../data/val/train`。如果实际路径不同，改配置里的 `data_dir`，不要挪数据。下载命令见 `loop_cluster/README.md`。
2. **跑通诊断脚本**，先用 `SandyResearch/parcae-140m`，一张卡就够，只需要验证集。跑通后再跑 `parcae-370m`、`parcae-770m`、`parcae-1.3b`，每个存一份 JSON。
3. **启动两个基线训练**：`launch_configs/parcae/pretrain/parcae-small-140m.yaml` 和 `gpt-small-140m.yaml`。
4. **把这几样东西报给用户**：
   - 训练的实际速度（tokens/秒）和总耗时，用来修正第 4 节的时间估计
   - 诊断输出的三张表（A、A2、B）
   - 集群有没有多节点训练组件

**诊断怎么判定通过**：在 4 倍压缩下，按 k-means 分组合并的损失上升，要明显小于按连续分块合并和按随机分组合并。不满足的话，"循环状态里有可利用的聚类结构"这个前提就站不住，要回头和用户重新商量方向。计划的判定日期是 2026-11-20。

**诊断脚本的工作方式**，改它之前先知道这几点：

- 它用一个包装对象替换模型实例上的 `update_recurrent_state`（`Parcae.iterate_forward` 每轮循环调用它一次），借此记录或修改每一轮之后的状态。
- 用 `num_steps_pair=torch.tensor([R, 0])` 强制跑固定的 R 轮。
- 循环状态是从随机噪声初始化的，所以每次前向之前都重新设随机种子，否则不同条件之间不可比。
- B 部分只合并前缀 token 的状态，只在后缀 token 上算损失，这样合并不会把未来信息泄漏给任何一个预测。
- 读数字时注意：Parcae 每轮都重新注入 token 级的 prelude 输出，所以被合并掉的状态能"免费"拿回自己的 token 身份，合并的代价会比没有注入的模型小。

## 6. 聚类怎么放进自回归模型：讨论到哪了

**核心矛盾**：视觉里"100 个 token 聚成 10 个、循环、再展开"在自回归里不能照搬。每个位置都要输出预测，且只能看过去；把所有 token 一起聚类再展开，会把未来 token 的信息泄漏回来。所以概念状态只能是"过去的摘要"，供后面的位置读取。

向用户提过三个候选，从保守到激进：

- **A. 循环内的因果聚类层**：每轮循环，token 软分配到 K 个概念；概念状态用前缀累积均值算（cumsum，天然因果）；token 再读回自己时刻的概念。不压缩序列。验证的是"概念表示本身有没有用"。风险是和线性注意力、Routing Transformer 这类工作相近，新意要靠"循环 = 聚类迭代"来立。
- **B. 分块边界概念**：每 C 个 token 聚成 m 个概念，深层循环只在概念序列上跑，token 通过注意力读之前块的概念。风险是最近一块没有深层计算；如果自然形成的簇本来就是连续片段，这就退化成 Hourglass / H-Net。
- **C. 可覆盖的槽记忆**：新 token 并入已有的概念槽并更新它，旧版本在注意力里被屏蔽，槽数固定则 KV cache 有上界。风险最大：硬分配不可导，工程量大。

我的建议是先做 A，但**用户还没表态**。还有一个问题在等用户回答：聚类的首要目标是"同算力下效果更好"还是"省计算和显存"。前者对应 A，后者对应 B 和 C，基线和指标都不一样。

诊断的 A2 表（相邻 token 落在同一簇的比例）会影响选择：比例接近 `1 - 1/r` 说明簇是连续片段，B 的新意有限；远低于它说明簇是跨位置的语义分组，A 和 C 才有独立价值。

**在用户定下方向之前，不要动手写聚类模块。** 可以讨论、可以做诊断类的小实验。

等真的开始写时，有两个已知的坑：

- **梯度到不了**：Parcae 训练时循环次数是随机采样的（均值 8），只对最后大约 4 轮做反向传播。聚类模块如果放在这个窗口之前，就拿不到梯度。
- **对比要公平**：所有结论都要在相同计算量下比，基线至少包括 Parcae、GPT、连续分块池化、随机分组。

## 7. 仓库里容易踩的地方

- 配置文件把数据路径写死为 `/resource/data/...`。仓库自己的启动脚本是把仓库本身挂载到 `/resource`；我们的 k8s 模板是把 PVC 挂到 `/resource`、仓库克隆到 `/resource/parcae`。两种都能用，但别混。
- 训练日志只走 W&B。模板里设了 `WANDB_MODE=offline`，要在线记录需要用户提供密钥。
- `.gitignore` 忽略了 `data`、`diagnostics/`、`experiments/`、`outputs/`、`tmp/`，以及 `*.csv`、`*.png`、`*.html`、`*.pt`、`*.parquet`、`*.log`、`*.pdf`。新建目录或想提交结果文件时注意别撞上。诊断的 JSON 不在忽略列表里。
- 仓库在容器里的安装方式是在根目录 `pip install -q -e .`。
